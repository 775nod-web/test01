# Fraud Decision Center（不正対策デモ）

不正リスクを見抜き、正常な顧客体験と事業成長を守る——国内のモバイル決済・デビットカード事業者向けに、
不正対策の将来業務を体験してもらう日本語デモアプリです。

> 本アプリはデモ用の合成データを使用しています。実際の取引判定や顧客データは含まれません。

---

## 1. デモの目的

不正を止めることだけでなく、正常な顧客の決済体験と事業成長を守るために、経営層と不正調査担当者が
どのような判断をより速く・より正確に行えるようになるかを、業務ストーリーとして体験してもらうことを
目的としたデモです。技術デモではなく、業務デモです。

伝える結論:

> 不正を多く止めることだけが目的ではありません。正常な顧客の取引を守り、調査担当者の判断を速め、
> 事業成長を止めないことが目的です。

## 2. 対象ユーザー

- CEO / CFO / COO / CRO などの経営層・不正対策責任者（概況ダッシュボードの想定利用者）
- 不正調査担当者・不正対策責任者（調査ワークベンチの想定利用者）

## 3. 実装範囲

- **Fraud Command Center（概況ダッシュボード）**: KPI、既存ルールのみ vs ルール＋AIの比較カード、
  不正率・正常承認率・損失額・リスクスコア分布のグラフ、高リスク取引一覧、調査キューの状況。
  期間・判定方式・チャネルのフィルターと連動。
- **Investigation Workbench（調査ワークベンチ）**: 優先度・ステータス・推奨アクション・リスクスコア帯・
  フリーテキスト検索によるケース一覧、ケース詳細（主要リスク要因、顧客の通常行動との差、直近24時間の
  取引タイムライン、直近7日間の要約、関連情報、判定根拠、操作履歴）、調査結果の登録（不正/正常/追加確認）。
- FastAPI製の合成データAPI（`/api/health`, `/api/dashboard`, `/api/cases`, `/api/cases/{id}`,
  `POST /api/cases/{id}/decision`）。

代表ケース`TXN-100123`（新規端末・深夜帯・短時間連続取引・地域乖離・高額取引が重なった案件）を中心とした
一貫したデモシナリオを実装しています。

## 4. 実装していない範囲

- データ取り込みパイプライン、Deltaテーブル作成、Sparkジョブ、Lakeflowパイプライン
- モデル学習、MLflow実験管理、Feature Store、Model Serving
- 外部LLM呼び出し、RAG、チャットボット
- 実運用の自動拒否制御・決済制御（調査結果の登録はUIのデモ表示であり、実際の取引には影響しません）
- 実顧客情報・実データ（すべて架空の合成データです）
- 認証の独自実装（Databricks Apps標準のアクセス制御に委ねます）

将来の本番構成では、これらの領域はUnity Catalogによるガバナンスや実際のモデルサービング基盤・
データパイプラインと連携する想定ですが、本デモのコードには含まれません。

## 5. 技術構成

```text
Databricks Apps (1 App / 1 Pythonプロセス)
└── bash -c "uvicorn main:app --host 0.0.0.0 --port $DATABRICKS_APP_PORT"
    └── FastAPI (backend/)
        ├── /api/health
        ├── /api/dashboard
        ├── /api/cases
        ├── /api/cases/{transaction_id}
        └── /api/cases/{transaction_id}/decision (POST)
    └── static/ (Reactビルド成果物。npm run build の出力先)
```

- フロントエンド: TypeScript + React + Vite + react-router-dom + recharts（軽量チャートライブラリ1種類のみ）
- バックエンド: Python + FastAPI + Uvicorn（Pydanticでレスポンス/リクエストモデルを定義）
- データ: すべて`backend/demo_data.py`内の固定・合成データ（日付をシードとした決定論的な疑似乱数）。
  DB・SQL Warehouse・Spark・外部APIには依存しない
- 状態: 調査結果の登録はメモリ内のみで保持（アプリ再起動でリセットされる想定、DBは使用しない）
- 認証: 追加実装なし。Databricks Appsの標準アクセス制御に委ねる
- CORS: 未実装（React/APIは同一オリジンで配信するため不要）

## 7. Databricks Free Edition上の前提

- Databricks AppsはApp数・連続稼働時間に制約があるため、**アプリは1つにまとめています**（React静的配信とAPIを同一プロセス・同一Appで提供）。
- SQL Warehouse、Model Serving、Lakebase、Unity Catalogテーブルは**必須にしていません**。
- 外部サービス・外部データベース・外部認証への依存はありません。
- アプリの状態（調査結果など）はプロセスメモリ内にのみ保持され、**アプリ再起動・再デプロイで消えることを前提**とした設計です。
- デモ実施前に、Databricks Apps側でアプリが起動していることを確認してください（Free Editionではスリープ/起動待ちが発生する場合があります）。

## 8. Databricks Appsでの作成・デプロイ方法

### 8.1 Databricks Appの作成

1. Databricksワークスペースの「Apps」から新規Appを作成します。
2. Appの種別は「カスタム(Custom)」を選択します（既製テンプレートは使用しません）。

### 8.2 ソースの配置方法

1. このリポジトリの内容一式（本READMEに記載した`app.yaml`・`requirements.txt`・`package.json`・
   `main.py`・`backend/`・`src/`等のファイル）を、Databricksワークスペース内の任意のフォルダ
   （Reposからのgit連携、またはワークスペースへの直接アップロード）に配置します。
2. 作成したAppの「ソースコードパス」として、上記フォルダを指定します。

### 8.3 デプロイ方法

1. Databricks Appsのデプロイ実行時に、`package.json`の`build`スクリプト(`tsc && vite build`)で
   Reactが`static/`にビルドされる前提です。Databricks Appsがビルドステップを自動実行するか、
   デプロイ前に`npm run build`を実行しビルド成果物(`static/`)を含めてソースを配置する必要があるかは、
   ご利用のDatabricks Appsのバージョン・公式ドキュメントに従って判断してください。
2. `requirements.txt`に基づきPython依存関係（`fastapi`・`uvicorn[standard]`・`pydantic`のみ）が
   インストールされます。
3. `app.yaml`の`command`に従い、`bash -c "uvicorn main:app --host 0.0.0.0 --port $DATABRICKS_APP_PORT"`
   でプロセスが起動します。
   > **重要**: `command`はYAML配列としてプロセスへ直接渡され、シェルを経由しないため、
   > `command`直下に`--port`, `${DATABRICKS_APP_PORT}`のように書いても環境変数は展開されません
   > （実機検証で`Invalid value for '--port': '${DATABRICKS_APP_PORT}' is not a valid integer`という
   > エラーで起動に失敗することを確認済みです）。必ず`bash -c "..."`の中で`$DATABRICKS_APP_PORT`を
   > 展開させる形にしてください。
4. `DATABRICKS_APP_PORT`という環境変数名がお使いの環境と異なる場合（Databricks Appsのバージョンにより
   名称が変わる可能性があります）は、`app.yaml`の該当箇所を実際の変数名に合わせて修正してください。
   固定ポート番号のハードコードはしないでください。

### 8.4 再デプロイ方法

ソースを更新した後、Databricks Apps側の「再デプロイ(Redeploy)」操作を実行してください。ビルドから
起動までの流れは初回デプロイと同じです。調査結果などのメモリ内状態は再デプロイ・再起動のたびにリセット
されます（仕様どおりの挙動です）。

### 8.5 アプリの起動方法・起動確認

Databricks Appsが払い出すURLへアクセスし、以下を確認します。

- `/` で概況ダッシュボード(Fraud Command Center)が表示される
- `/cases` で調査ワークベンチのケース一覧が表示される
- `/cases/TXN-100123` で代表ケースの詳細が表示される
- `/api/health` が `{"status":"ok","service":"fraud-decision-center",...}` を返す
- ブラウザの開発者コンソールにエラーが出ていない

## 9. アプリの使い方

### 9.1 概況ダッシュボード（Fraud Command Center）の使い方

グローバルナビゲーションの「概況」から開きます（トップページ `/`）。

1. 画面上部のフィルターで「期間」(過去7日/過去30日)・「判定方式」(既存ルールのみ/ルール＋AI)・
   「チャネル」(すべて/モバイル決済/デビットカード)を切り替えると、KPI・比較カード・グラフ・
   高リスク取引一覧がすべて連動して更新されます。
2. 上段の4つの大きなKPI（推定防止損失額・正常取引承認率・誤検知率・平均検知時間）が最重要指標です。
   各KPI右上の「?」ボタン（クリックまたはEnter/Spaceキー）で説明を表示できます。
3. 「既存ルールのみ vs ルール＋AI」カードで、判定方式による捕捉率・承認率・誤検知率・損失・調査時間の
   違いを比較できます。
4. グラフは、不正率・正常承認率の推移、不正損失額・推定防止損失額の推移、リスクスコア帯別の
   正常・不正分布（正常/確定不正それぞれの母集団に占める割合）を表示します。
5. 「高リスク取引一覧」の行を選択（クリックまたはEnter/Spaceキー）すると、該当ケースの調査詳細画面
   （`/cases/{取引ID}`）へ遷移します。代表ケース`TXN-100123`は常に先頭に固定表示されます。

### 9.2 調査ワークベンチ（Investigation Workbench）の使い方

グローバルナビゲーションの「調査ケース」から開きます（`/cases`）。

1. 一覧画面で「優先度」「ステータス」「推奨アクション」「リスクスコア帯」「フリーテキスト検索」
   （取引IDまたは加盟店名の部分一致）により、12件の調査ケースを絞り込めます。
2. 行を選択（クリックまたはEnter/Spaceキー）すると、ケース詳細画面（`/cases/{取引ID}`）へ遷移します。
3. 詳細画面では、取引サマリー・主要リスク要因・顧客の通常行動との差・直近24時間の取引タイムライン・
   直近7日間の要約・関連情報（カード/端末/口座/加盟店）・判定根拠（既存ルール該当理由・AIスコア上位要因・
   モデルバージョン・判定日時・データ更新時刻）・操作履歴（デモ用監査情報）を確認できます。
   「完全な監査機能」とは表現せず、本番構成ではUnity Catalog等のガバナンス機能と連携する想定である旨を
   明記しています。
4. 画面下部の「調査結果入力」から、不正・正常・追加確認のいずれかを選択し、任意のメモを入力して
   「調査結果を登録」ボタンで登録できます。登録後はトースト通知が表示され、ステータスが「完了」に更新され、
   操作履歴に記録が追加されます。
5. 概況ダッシュボードの「調査待ち件数」や高リスク取引一覧のステータスも、ワークベンチでの調査結果登録に
   連動して更新されます（同一プロセスのメモリ内状態を共有しているため）。

## 10. 10分デモ手順

アプリ内にデモガイド画面は設けていません。以下の手順に沿って、概況ダッシュボードと調査ワークベンチを
直接操作してデモを進めてください。

1. 概況画面で「既存ルールのみ」を表示する。
2. 正常承認率と誤検知率を確認する（既存ルールだけでは正常な顧客も一定数止めていることを伝える）。
3. 「ルール＋AI」へ切り替える。
4. 改善の経営インパクトを説明する（不正捕捉率を大きく落とさず、正常承認率が上がり誤検知率が下がる）。
5. `TXN-100123`を開く（高リスク取引一覧の先頭、または調査ケース一覧から）。
6. 複数のリスク要因（新規端末・深夜帯・短時間連続取引・地域乖離・金額超過）が重なって判断されている
   ことを確認する。
7. 調査結果を登録する（不正・正常・追加確認のいずれかを選び、トースト通知とステータス更新を確認する）。
8. 判定根拠（既存ルール該当理由・AIスコア上位要因・モデルバージョン）と操作履歴（デモ用監査情報）を
   確認する。

話すメッセージ:

- 不正率だけを最適化すると、正常な顧客を止めてしまう可能性がある。
- ルールとAIの組み合わせにより、不正損失と顧客体験を同時に管理できる。
- 調査担当者は情報収集ではなく、判断そのものに時間を使えるようになる。
- 調査結果を将来の検知改善へフィードバックする仕組みを想定している。
- 本番導入前のPoCでは、実際の顧客データを用いて経済価値（不正捕捉率・誤検知率・正常承認率・
  推定防止損失・調査時間・判定時間）を検証する。

Databricks Apps上での動作確認が最終確認事項ですが、開発中は下記の手順によりローカルで静的整合性・

```bash
# バックエンド
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 別ターミナルでフロントエンドをビルド
npm install
npm run build   # static/ にビルド成果物を出力

# ブラウザで http://localhost:8000/ にアクセス
```

`npm run dev`で開発サーバーを起動する場合、`vite.config.ts`の`server.proxy`設定により`/api/*`は

## 13. 合成データとセッション内状態に関する注意

- すべてのKPI・取引・顧客情報は架空の合成データです。実データ・個人情報は一切使用していません。
- 顧客は`CUST-XXXX`形式の匿名ID、カードは末尾4桁のみを表示します。
- 日次の集計値は、日付文字列をシードとした決定論的な疑似乱数で生成しており、同一条件
  （シナリオ・期間・チャネル）であれば常に同じ結果を返します（サーバー再起動をまたいでも同様）。
- 調査ケース一覧・詳細・調査結果はアプリプロセスのメモリ内にのみ保持されます。アプリの再起動・
  再デプロイ・スケールで内容がリセットされます。これは仕様どおりの挙動であり、データベースや
  永続ストレージは使用していません。
- リスクスコア・推奨アクションは「不正を確定するもの」ではなく、調査判断の補助情報として提示しています。

### 実施できなかったこと・正確なエラー

- 本セッションの実行環境は、外部ネットワークアクセスがプロキシ経由に制限されており、
  `*.cloud.databricks.com` / `*.azuredatabricks.net` 等のDatabricksホストへの接続は
  プロキシポリシーにより拒否されました。

  ```text
  $ curl -v https://dbc-xxxxxxxx-xxxx.cloud.databricks.com/api/2.0/apps
  ...
  < HTTP/1.1 403 Forbidden
  * CONNECT tunnel failed, response 403

  $ python3 -c "urllib.request.urlopen(...)"
  URLError: <urlopen error Tunnel connection failed: 403 Forbidden>
  ```

- そのため、Databricks CLIまたは REST API 経由でのApp作成・ソース配置・デプロイ・起動確認のいずれも
  本セッションからは実行できませんでした。

### 利用者による実機デプロイで判明した問題と対応（追記）

利用者がDatabricksワークスペースへRepos経由でこのリポジトリを配置し、実際にデプロイを実行したところ、
以下のエラーで起動に失敗しました。

```text
Error: Invalid value for '--port': '${DATABRICKS_APP_PORT}' is not a valid integer.
```

**原因**: `app.yaml`の`command`はYAML配列としてプロセスへ直接渡され、シェルを経由しないため、
`${DATABRICKS_APP_PORT}`という記法は展開されず、文字列そのままがuvicornの`--port`引数に渡っていた。

**対応**: `app.yaml`を、`bash -c`経由で環境変数を展開する形に修正済み。

```yaml
command:
  - bash
  - -c
  - "uvicorn main:app --host 0.0.0.0 --port $DATABRICKS_APP_PORT"
```

修正後の再デプロイ結果は、確認でき次第本セクションに追記します。

### 必要な利用者操作

デプロイを完了するには、Databricksワークスペースへ到達可能な環境（利用者のマシン、または
Databricksに接続可能なCI/CD環境）で、本README「8. Databricks Appsでの作成・デプロイ方法」の手順を
実行してください。実機での動作確認後、下記が生じた場合は本READMEのトラブルシューティングを参照し、
それでも解決しない問題があれば、エラーメッセージとともに追記してください。

## 16. トラブルシューティング

| 症状 | 想定原因 | 対処 |
|---|---|---|
| アプリ起動直後に`static/`が見つからない旨のJSONが返る | Reactのビルドが実行されていない、またはビルド成果物がデプロイに含まれていない | `npm run build`を実行し、生成された`static/`をデプロイ対象に含める。Databricks Appsがビルドを自動実行する設定か確認する |
| `Error: Invalid value for '--port': '${DATABRICKS_APP_PORT}' is not a valid integer` で起動失敗 | `app.yaml`の`command`を配列の直書きにしていると、シェルを経由しないため`${DATABRICKS_APP_PORT}`が展開されず文字列のまま渡ってしまう（実機で確認済みの不具合） | `app.yaml`を`command: [bash, -c, "uvicorn main:app --host 0.0.0.0 --port $DATABRICKS_APP_PORT"]`の形にする（本リポジトリは対応済み） |
| その他のポート起動エラー | `DATABRICKS_APP_PORT`の環境変数名が実際の環境と異なる | Databricks Appsのログで実際の環境変数名を確認し、`app.yaml`を修正する |
| `/api/*`が404になる | リバースプロキシ等でパスが書き換えられている、または`main.py`が正しくデプロイされていない | Appのソースパス・起動コマンドが`app.yaml`どおりか確認する |
| 画面の表示が英語のままになる/文字化けする | ブラウザのキャッシュ、または文字コードの問題 | ハードリロードする。レスポンスがUTF-8で返っているか`/api/health`で確認する |
| 調査結果を登録しても他の利用者に反映されない | 仕様どおりの挙動（セッション内・プロセスメモリ内保持） | 複数プロセス/複数インスタンスで動作している場合、状態は共有されません。デモでは1インスタンスでの利用を想定してください |
| デプロイ直後に前回の調査結果が消えている | 仕様どおりの挙動（再デプロイ・再起動でメモリ状態がリセットされる） | デモ前に毎回、代表ケース`TXN-100123`等で動作確認してください |
