# Architecture

## End-to-end data flow

```text
notebooks/lib/datagen.py (deterministic, pure Python)
        │
        ▼
notebooks/01_generate_synthetic_data.py  →  Bronze Delta tables
        │
        ▼
notebooks/02_build_silver_and_gold.py    →  Silver tables + Gold customer_360
        │
        ▼
notebooks/03_build_risk_and_retention.py →  Gold retention_action_list, executive_kpis
        │
        ▼
sql/queries/*.sql  (Phase 5 — parameterized read queries)
        │
        ▼
backend/services/*.py  →  backend/main.py (/api/*)
        │
        ▼
frontend/src (React) — 5 pages, built to backend/static/
```

## Catalog/schema layout

Notebooks resolve the target location at runtime rather than assuming it
(`notebooks/lib/catalog_utils.py`):

- Unity Catalog available: `{UC_CATALOG}.bronze` / `.silver` / `.gold`
  (default `UC_CATALOG=bank_demo`).
- Unity Catalog unavailable: Hive metastore databases
  `{UC_CATALOG}_bronze` / `_silver` / `_gold`.

The backend (`backend/db.py`) does the equivalent resolution once at
startup: it tries `{catalog}.gold.executive_kpis`, and falls back to
`{catalog}_gold` if that fails.

## Backend service layout

- `backend/main.py` — FastAPI app, route handlers, static file serving.
- `backend/config.py` — settings from environment variables only.
- `backend/db.py` — query engine abstraction:
  - `DatabricksQueryEngine`: production path. Authenticates via the
    Databricks SDK's default credential chain (`databricks.sdk.core.Config().authenticate`)
    — no static tokens in source. Connects with `databricks-sql-connector`
    to the SQL warehouse attached as an app resource.
  - `LocalDuckDBQueryEngine`: dev-only fallback reading
    `backend/local_fixtures/*.parquet` (generated by
    `scripts/generate_local_fixtures.py`) via DuckDB. Automatically
    selected when `DATABRICKS_SERVER_HOSTNAME`/`DATABRICKS_HTTP_PATH`
    aren't set — never used in a deployed Databricks App with a SQL
    warehouse resource attached.
  - Both engines execute the exact same `sql/queries/*.sql` files with
    named parameters (`:param`); only the schema-prefix substitution and
    parameter-marker translation differ internally.
- `backend/schemas.py` — Pydantic response models, one per endpoint.
- `backend/services/` — thin wrappers mapping query results to typed
  responses: `analytics.py` (Executive Overview), `customers.py` (Segment
  Explorer, Customer 360), `retention.py` (Retention Actions + CSV
  export), `poc.py` (PoC & Future Expansion).

## Frontend structure

- `frontend/src/App.tsx` — `HashRouter` (avoids needing server-side path
  routing behind the Databricks Apps proxy) with 5 routes.
- `frontend/src/pages/` — one component per page.
- `frontend/src/components/` — shared `Layout`, badges, loading/empty/error
  states, `KpiTile`, `BarChart`, `ValueRiskMatrix`, `TrendChart`.
- `frontend/src/api/client.ts` — typed fetch wrapper, one function per
  endpoint.
- `frontend/src/styles/global.css` — the CLAUDE.md §7 palette as CSS
  variables; every color is paired with a direct text label or badge text
  (never color-alone), per the dataviz design check run during Phase 6.

## Deployment topology

```text
React (built to backend/static/, HashRouter)
          │  same-origin fetch("/api/...")
          ▼
FastAPI (backend/main.py, python -m backend.main)
          │  databricks-sql-connector + SDK auth
          ▼
Databricks SQL warehouse (attached app resource)
          │
          ▼
Gold Delta tables (Unity Catalog or Hive metastore)
```

See `README.md` for the exact Databricks Apps deployment steps and
`docs/free-edition-limitations.md` for what this build could not verify
directly (no network path to any Databricks workspace from the coding
session).
